# AI accounts, files and calendar integrations: feasibility decisions

Research checked September 5, 2026 using official provider documentation. This records supported directions and proposed implementation choices; no account was connected, no credentials were read, and no provider integration was executed.

## Can users sign in to their own AI account?

Yes, there are viable account-based paths, but each provider's product and billing model matters. “Use my ChatGPT” must identify whether Remind Me is embedding Codex, using the OpenAI API, or running as an app inside ChatGPT. Those are distinct integrations.

| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- |

This uses the Codex runtime and eligible ChatGPT account entitlements. It is not a general ChatGPT-web API. [App Server](https://learn.chatgpt.com/docs/app-server)                                        | Prototype an optional desktop adapter. ### Proposed ChatGPT/Codex experiment

Time-box this as an engineering spike, with a written pass/fail report rather than a release promise. Use the documented managed login so the runtime owns its credentials and renewal. Do not copy cookies, scrape ChatGPT, collect passwords or reuse another application's auth files.

Use an isolated per-app runtime/configuration directory and a version-pinned protocol adapter. Keep the app-server transport private to the desktop process. Expose only the small subset of protocol operations the chat UI needs. The docs contain powerful shell and execution operations; a reminder app must not expose those to the model or renderer. Some integration surfaces, including dynamic tools, are experimental. [Codex App Server reference](https://learn.chatgpt.com/docs/app-server)

Required experiment outcomes:

1. Login, cancellation, logout and token refresh work with an explicitly chosen test account; report eligible plan/model behavior actually observed.
2. Stream ordinary conversation, cancel a turn, restart and resume a conversation, and show quota exhaustion without losing the draft.
3. Enforce a real process/tool boundary: no shell, arbitrary filesystem access, inherited personal plugins, unrelated account configuration or direct database authority. An empty working directory alone is insufficient. If the pinned runtime cannot enforce the required restriction, do not ship this adapter.
4. Connect only read-only calendar retrieval and validated proposal generation; prove adversarial prompts cannot bypass review. Experimental APIs must be version-gated, or use a supported integration alternative.
5. Confirm packaging/update obligations and distribution terms for the selected version. Successful authentication alone is not a legal or operational release determination.

The proposed product label is **Connect ChatGPT through Codex**, accompanied by a brief explanation of what account usage it consumes. Direct API use stays a separate option. A browser-hosted Remind Me deployment would require a different server/session architecture; the local runtime experiment does not establish hosted multi-tenant support.

### Credential and privacy design

Store user-owned desktop API keys in OS-protected storage, with request execution in main/a restricted utility service. Never bundle a developer's production key in the application, expose stored secrets in renderer state, or include them in backups/logs. A hosted app must keep provider secrets on a secured server with authenticated user isolation. OpenAI explicitly warns against exposing API keys in client code. [API authentication](https://developers.openai.com/api/reference/overview)

Use system-browser OAuth, PKCE/state where supported, a strict callback policy, cancellation/expiry and explicit disconnect. The Canvas service's protected-secret abstraction is a useful starting pattern. Treat calendar feed URLs as credentials too.

Show which provider receives a prompt, selected attachments and scoped calendar facts. Online chat can work without uploading the whole calendar. Default to the minimum context needed; require an explicit choice before uploading document bytes or switching destinations. Record optional usage locally without prompt telemetry. Review provider retention settings before making any deletion/retention promise.

## Can users import Canvas and other calendars?

Yes. The app already has ICS import and selected Canvas assignment import. Subscription and sync are additional capabilities, with external identity and update handling as prerequisites.

| Connection              | Feasible scope                                                                   | Product and engineering caveat                                                                                                                                                                                                                                                       |
| ----------------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| ICS file                | One-time import from a downloaded calendar                                       | No future updates. Fix recurrence fidelity and repeat-import identity first.                                                                                                                                                                                                         |
| Canvas calendar feed    | Read-only subscription to Canvas events and assignments                          | Feed scope is bounded; it is not an exhaustive task/archive API. Keep course/source identity and display last refresh. [Canvas calendar-feed guide](https://community.instructure.com/en/kb/articles/662804-unknown)                                                                 |
| Canvas API              | Assignments plus calendar events, subject to user permissions and enabled scopes | Multi-user apps need OAuth onboarding and an institutional/developer-key strategy. [OAuth overview](https://developerdocs.instructure.com/services/canvas/oauth2/file.oauth), [Calendar Events API](https://developerdocs.instructure.com/services/canvas/resources/calendar_events) |
| Google Calendar         | Authorized calendar/event read sync; later optional write sync                   | Use incremental sync, reconcile deletions, and recover invalid cursors with a full resync. [Synchronization guide](https://developers.google.com/workspace/calendar/api/guides/sync)                                                                                                 |
| Outlook / Microsoft 365 | Microsoft Graph calendar-view read sync                                          | Persist delta links per calendar/time range; consume all pages. [Calendar-view delta](https://learn.microsoft.com/en-us/graph/delta-query-events)                                                                                                                                    |

Canvas's OAuth documentation states: “asking any other user to manually generate a token and enter it into your application is a violation of Canvas' API Policy.” It also requires OAuth for applications used by multiple users. The application currently asks for a token in its Settings connection form. This is a specific provider policy issue for wider release; the documentation separately permits manual tokens for developer testing. [Manual token generation](https://developerdocs.instructure.com/services/canvas/oauth2/file.oauth#manual-token-generation)

The Canvas feed guide describes a window of 30 past days and 366 future days, up to 1,000 items, and excludes To Do items. Consequently, absence from a refresh must not automatically delete a local reminder: the source may simply have rolled out of the feed's window. Verify the institution's available feed and courses during onboarding. [Canvas feed guide](https://community.instructure.com/en/kb/articles/662804-unknown)

For Canvas OAuth, do not embed an institutional client secret in the desktop binary. Confirm the supported native/public-client flow for the institution; use a confidential broker when the required token exchange needs a secret. This adds hosting, operational and privacy responsibilities. Feed subscription is a useful near-term option where an OAuth developer key cannot be obtained.

Proposed rollout: fix ICS semantics and identity; add protected feed subscriptions; implement a reviewed Canvas OAuth pilot; then Google and Outlook read sync. Use incremental/delta cursors for APIs, bounded polling while the app is running, retry/backoff and a clear last-successful-sync display. Validate Google's/Microsoft's registered-app consent and least-privilege scopes during each integration spike. Full push notifications require reachable webhook infrastructure; they do not make a fully offline desktop automatically update.

Store provider/account/calendar/event identity, recurrence-instance identity, version/ETag, last imported base, local overrides and tombstones. Preserve completion, local notes and reminder choices when source dates change. Treat partial fetches and authorization failures as incomplete refreshes, never deletion signals. Two-way edits need conflict resolution and outbound idempotency as a separate milestone.

## Can it understand any image or PDF?

It can support much broader intake than it currently does, but no model guarantees perfect interpretation of arbitrary files. The current implementation is strongest at extracting schedules from readable PDF text or English OCR.

OpenAI documents image inputs for PNG, JPEG, WebP and non-animated GIF, and PDF inputs with text/image processing on eligible models. Model capability and provider limits must be checked by the adapter. File acceptance alone does not prove accurate extraction of a due date or recurrence. [Images and vision](https://developers.openai.com/api/docs/guides/images-vision), [File inputs](https://developers.openai.com/api/docs/guides/file-inputs)

Proposed intake layers: normalize formats locally; run native PDF text/OCR; let users ask questions or request extraction; optionally send selected pages to a vision-capable provider; attach visible evidence and uncertainty to every proposed calendar field; confirm through the existing import transaction. Keep malformed-file, unsupported-codec, password, size and no-readable-content outcomes distinct.

Do not increase the existing 25 MiB/20-page limits blindly. Page selection and bounded chunks can make large documents useful without unbounded decoding, memory or API costs. HEIC/TIFF conversion, language packs, handwriting quality and retained attachments need their own validation corpus and lifecycle policy.
